# Оцінювання пошуку на золотому наборі (Результат 5, C1–C4)

**Артефакти:** `eval/gold.jsonl`, `eval/annotator_agreement.jsonl`, `src/eval_metrics.py`, `outputs/eval_results.json`, `docs/fig_eval_comparison.png`.

## 1. Склад золотого набору (C1)

Створено **45 тестових запитів** (вимога: $\ge 40$) із ручною перевіркою релевантних документів:
- **20 запитів за ключовими словами / кодами** (`G01`–`G20`): точні коди виділів, квитків, латинські назви видів, цифрові пороги.
- **10 перефразованих запитів** (`G21`–`G30`): формулювання природною мовою без дослівного повторення термінів тексту.
- **9 багатокрокових (multi-hop) запитів** (`G31`–`G39`): потребують поєднання фактів із 2–3 документів.
- **6 запитів без відповіді** (`G40`–`G45`, вимога: $\ge 5$): поза межами корпусу (зарплата лісника, облік вовків, держномери лісовозів, глибина снігу на Говерлі, експортне мито на фанеру, вилов форелі).

## 2. Узгодженість двох розмітників — Cohen's $\kappa$ (C2)

Двоє незалежних розмітників оцінили релевантність (`0` / `1`) на **15 запитах** (45 пар запит–документ у `eval/annotator_agreement.jsonl`, вимога: $\ge 10$ запитів):
- Спостережувана узгодженість: $p_o = 42 / 45 = \mathbf{0.9333}$
- Очікувана випадкова узгодженість: $p_e = \mathbf{0.5086}$
- **Коефіцієнт Коена:** $\kappa = \frac{p_o - p_e}{1 - p_e} = \mathbf{0.8643}$

Значення $\kappa = 0.8643 > 0.80$ відповідає рівню **майже повної узгодженості (almost perfect agreement)** за шкалою Ландіса–Коха; 3 розбіжності стосувалися опосередкованих посилань і були узгоджені під час фінальної ревізії золотого набору.

## 3. Порівняння 4 конфігурацій пошуку (C3)

Оцінювання виконано на 39 відповідаємих запитах (метрики ранжування) + 6 запитах без відповіді (`NoAns` — частка коректно відхилених запитів за порогом впевненості):

| Конфігурація | Recall@5 | Recall@10 | MRR | nDCG@10 | Відсікання `no-answer` | Сер. затримка (ms) | P95 затримка (ms) |
|--------------|---------:|----------:|----:|--------:|-----------------------:|-------------------:|------------------:|
| `BM25` | 0.8718 | 0.9103 | 0.8782 | 0.8654 | 0.5000 | **0.133** | 0.16 |
| `Dense` (`SVD-CharWord-256d`) | 0.9359 | **0.9615** | **0.9701** | **0.9372** | 0.5000 | 1.145 | 1.48 |
| `Hybrid (RRF k=60)` | 0.9103 | 0.9487 | 0.8974 | 0.8895 | 0.0000* | 1.378 | 1.69 |
| **`Hybrid + Rerank (top-30→5)`** | **0.9487** | 0.9487 | 0.9380 | 0.9192 | **0.6667** | 4.137 | 5.12 |

*\*Примітка:* чистий RRF використовує лише ранги ($1/(60+r)$), тому навіть нерелевантний запит отримує фіксований максимальний скор ~0.0328 і не може надійно відсікати `no-answer` без каліброваного скору reranker або dense.

## 4. Вибір конфігурації для ЛР 11 (RAG): якість, затримка й вартість (C4)

Для побудови RAG-системи в **ЛР 11** обираємо конфігурацію **`Hybrid + Rerank (BM25 + Dense + RRF k=60 + Reranker top-30→5)`** із обов'язковим метаданим `pre-filter` за `sensitivity`:
1. **Якість (Recall@5 та відсікання галюцинацій):** для RAG найкритичнішою метрикою є `Recall@5` (чи потрапить потрібний факт у контекстне вікно LLM) та здатність розпізнати запит без відповіді. `Hybrid + Rerank` показав **найвищий `Recall@5 = 0.9487`** і **найкраще відсікання `no-answer` (66.7 %)**, поєднуючи точність BM25 на кодах (`V-102`, `ЛК-2026-047`) із семантичною стійкістю Dense.
2. **Затримка:** у локальному режимі середня затримка становить **4.14 ms** (при використанні нейромережевого `multilingual-e5-small` + `CrossEncoder` на CPU — орієнтовно **80–180 ms** на запит), що становить менше 5–10 % від часу генерації відповіді LLM (1–3 секунди) і є цілком прийнятним для інтерактивного користувача.
3. **Вартість:** усі компоненти (`FAISS`, `rank_bm25`, `intfloat/multilingual-e5-small`, open-source `CrossEncoder`) працюють **локально безкоштовно ($0 за 1000 запитів)** без передачі `internal`/`restricted` даних лісгоспу у зовнішні хмарні API embeddings. Крім того, відсікання нерелевантних чанків на етапі reranking (топ-5 замість топ-10) зменшує витрати вхідних токенів LLM у ЛР 11 приблизно вдвічі.
